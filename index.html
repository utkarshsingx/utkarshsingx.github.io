// HOW I WORK

I take things from a blank repo to a live multi-tenant product and then stay on them — the unglamorous half. Most of my year goes into platforms that several organisations use at once, where one badly scoped query leaks another tenant's data and one unguarded deploy drops a live class.

So I work in evidence. Before a fix ships I want the failing query, the rendered pixels, the row count. A check that cannot fail is not a check. That habit is why the numbers on this page are pulled from the GitHub API rather than typed by hand.

// ARCHITECTURE — HOW I BUILD PLATFORMS

MULTI-TENANT REFERENCE PATTERN

How I architect
multi-tenant platforms.

Same shape every time: thin clients, one authenticated gateway that resolves the tenant before anything else touches the database, domain services behind it, a worker tier for everything slow, and durable state in Postgres + Redis + S3. The diagram is the reference pattern — it has carried an LMS fleet, an assessment engine and a compliance product.

// THE TENANT RESOLVER

Tenancy is resolved once, at the edge, and carried as request state — never re-derived in a view. Every query is scoped from it. The expensive lesson behind that line: a filter applied one layer too late is a cross-tenant leak, and it will not show up in tests that only ever run as one tenant.

  • Layered shape · portable across products
  • Tenant resolved at the edge · never in a view
  • Slow work is queued · Celery + Redis + beat
  • Rolling deploys · circuit-breaker rollback

// APPENDIX — FREQUENT QUESTIONS

6 ANSWERS

The
quick answers.

The things people ask before the first call, answered here so the call can be about something else.

Q1What are you working on right now?
Three products in parallel. A multi-tenant learning platform at AI Linc, where I lead the backend and most of what runs on it; Prephasz, a campus-placement platform I founded the engineering for and still own end to end; and Audix GRC, a compliance automation platform I joined at the blank-repo stage.
Q2What do you actually own, day to day?
Backend first — schema, API, queues, deploys — but I do not hand off at the API boundary. In practice a feature is mine from the migration through the React or React Native screen to the rolling deploy and the dashboard that proves it worked. The architecture in §03 is the shape I keep returning to because I have had to operate all of it.
Q3Are you open to new work?
Open to conversations about platform engineering, backend and AI infrastructure — particularly multi-tenant products where correctness matters more than novelty. Email is the fastest route and I answer within a day.
Q4Where are you, and how do you work?
Greater Noida, India, on IST (GMT+5:30), remote-first. The teams I ship with sit in Hyderabad, Pune and Dubai, so most of my working life is asynchronous by default — written decisions, reproducible evidence, and a deploy anyone can roll back.
Q5What is your stack of choice?
Django REST or NestJS, PostgreSQL, Celery and Redis, React or Next.js, React Native on Expo, containers on ECS Fargate. Deliberately boring infrastructure under deliberately interesting products — the novelty budget belongs in the thing users touch, not in the queue.
Q6Why are the numbers on this page so specific?
Because they were read, not estimated. Every figure in §04 came from the GitHub contributions API on 29 October 2026, for the trailing twelve months. If a claim on this page cannot be reproduced from a public source, it is not on this page.
